# Run operations and read model

Use `workflow{action:"run", graph:<object>}` (or `from:<saved-name>`, or `graph_path:<absolute-local-JSON-file>`), then `status` and `wait` with the returned `run_id`. For a reusable graph, `save` first and `run from:<name>` next; `library` lists it. `graph_path` is for an unsaved caller-authorized local file on run/save/amend, not a remote path. `/wf` is an optional shelved-graph front door.

A run may be running, held, interrupted, done, failed or stopped. Running requires a live process with the exact runner command and run identity; a persisted PID or parked marker is not sufficient. Held gates and interrupted runs do not count as running. List responses include full-census `counts` and `total` even when the recent-runs page is truncated. `interrupted` means unfinished work with no live runner: inspect saved outputs and uncertain side effects before explicitly resuming with `wait`. A recorded fatal runner crash is `failed` and needs correction/amend rather than repeated wait/respawn. Every `status`/`wait` payload carries the derived `next` — do what it says and `wait` again until it is empty (`wait` self-yields with a "call wait again" note before a terminal state to stay inside the host deadline). On a held gate `next` names the gate and its options: ask the owner, then `release` with the exact answer. A machine gate may park without a child; read its check attempt, last exit/tail and deadline.

`status.nodes` uses committed results for scheduling and projects an uncommitted child spawn as running only when its recorded process identity is still verified. `blocked_by` points to unfinished ancestors. Child spend metrics are cumulative across attempts/graph amendments. Liveness and heartbeat come only from exact, currently verified child process/session identities: `active_spawns` lists all active fan-out children, while `active_spawn` retains the first for existing consumers. Node and per-item metrics do not count old unended database rows as live; missing current activity means unknown idle, not zero. Not every run has a metrics row. Missing API-call evidence is unknown, never zero; retry after uncertain effects may duplicate them. Failed and partial nodes ship `node_facts` (`error_class`, `attempts`, `attempts_log`, the child's `final` words, `log_path`, `prompt_path`) beside the error line. A turn-cap death (`cap_exhausted`) is typed only when the child's core quiet-turn report carries the loop's own budget stamp (`max_iterations_reached(n/m)`); prose about turn limits is never trusted, and an untyped budget death stays `unknown`. Stale runner exits do not suppress amended work. A pruned/skipped node is terminal, not done output.

`steer` queues text for a future child spawn; it does not inject into a running child or reopen a terminal run. To change a graph, submit the entire replacement via `amend`; `dry_run:true` previews added/removed ids plus changed/will_rerun/unchanged. Added nodes and their downstream work appear in `will_rerun`; matching committed results replay-skip. Stop is not rollback; reconcile external effects before rerunning.

## Small, parent-gated escalation recipe (no new engine feature)

Use a terminal, decision-only agent node with no automatically runnable work descendants. Its ordinary schema-defined final JSON can contain `needs_escalation: true` and a short reason (the node schema must actually permit these fields). The parent inspects that exact value and any external effects, selects an explicit model and amends the graph with original committed inputs plus a bounded factual handoff. Check `dry_run`'s `will_rerun` before applying. A timeout remains a failed node, not a safe auto-retry: the parent investigates and decides. Never use this on a work-product node with downstream execution; schema-valid JSON is committed as done even if its text requests escalation. This recipe adds no tool, status, automatic fallback or guarantee of side-effect rollback.

Desktop cards use `::workflow{id="<run_id>"}`: paste the `card` line every `run`/`status`/`wait` payload carries, alone on its own line. The card is agent-authored — the backend never appends it. Backend and desktop plugin installations are separate.

`profile` routes an agent node to a named target profile, not a fan-out item: the child gets the TARGET's SOUL, memory, `.env` and tools. This is delegation, not isolation. Before launching, the target owner writes `<target_profile_home>/workflow_team.json` as `{"accept_from":["<launcher-profile-name>"]}`; the launcher name comes from the door's own HERMES_HOME (for the default profile, use `"default"`), never from a graph argument. The target must have `config.yaml`; `default` may launch but is never a target. Without target-owned consent validation fails before any run write/spawn; a target deleted before Popen fails with `error_class:"spawn"`, never silently falling back to the launcher.

## Lanes: in-flight dedupe for pollers

`run` accepts an optional `lane_key` (≤128 chars) and `status` accepts `lane_key` as an alternative to `run_id` (never spawning anything). The registry is an advisory index under a per-key kernel lock: while a claim is held, a second `run` with the same key never spawns — the UNFINISHED INCUMBENT WINS. Dedupe response: `{deduped:true, run_id, state, runner_live, needs_resume, last_event_ts, hint}` with the incumbent's ids, regardless of runner liveness — an interrupted incumbent is RESUMED (`wait run_id=<id>`), never replaced; resume stays with `wait`/keeper under the existing per-run flock. `stop` on the incumbent is the explicit abandonment: terminal `stopped` releases the key and the next claim creates a fresh run. Keys are global per runs root — callers prefix `<team>/` themselves. Entries are append-only (never deleted); a stored key must equal the supplied key exactly (collision → error, never dedupe against a different key). `status lane_key=<key>` answers `{lane_key, run_id, state, runner_live, unfinished, needs_resume, last_event_ts}` (runner_live is /proc truth, not a persisted marker; `needs_resume` = unfinished AND runner dead — the poller's signal to `wait`); an unseen key returns `run_id:null, unfinished:false`. `list` rows carry `lane_key`/`team` when present. A `team` label (≤64) on `run` stamps run.json and shows in `list`; it changes nothing about scheduling.

## Flock law: liveness, the child-probe rule, and `release-lock`

The runner (`wf.py run <id>`) takes an exclusive `flock` on `<run>/runner.lock` for its whole life; the kernel drops it on any exit (clean, crash, SIGKILL) and enforces it across every pid namespace sharing the mount, so HELD lock = live runner, unconditionally (the cross-container law; the pid-identity check is only the fallback for an unheld lock). The admission path retries `LOCK_EX|LOCK_NB` a bounded 3×10 ms before an honest `WORKFLOW_BUSY` exit. Every consumer (`status`, `wait`, `list`, lane `status`) reads the ONE published `runner_live` field of a single `run_state` — one call, at most one probe — never a second probe of its own, because a re-probe microseconds later can flip across a dying runner's release and leave status and liveness disagreeing.

**Probe via child; the parent never holds.** A long-lived process (the tool door inside the gateway, a dashboard, a poller) never opens `runner.lock` itself. The probe is a short-lived child (`flock -n <lock> true`, or an equivalent `-I -S` Python one-liner where util-linux is absent) that opens the file, takes `LOCK_EX|LOCK_NB`, and exits — its death is the release. The child inherits nothing (closed fds, empty environment, `/dev/null` stdio) and is bounded by a timeout; a missing lock file reads `missing` and is never created (read paths must not litter historical runs). Why: a door that held the probe fd in-process and was SIGKILLed mid-probe during a gateway sweep — with the fd inherited across a spawn into another pid-namespace view — left the lock held by nobody visible: `/proc/locks` showed no line for the inode, no `/proc/*/fd` pointed at the path, the runner pid was dead, and wait-resume was wedged until the work was re-run under a new lane key. With the probe in a child, no SIGKILL of the parent at any instant can strand a lock the parent never owned.

**`release-lock` escape hatch** (`python3 wf.py release-lock <run_id>`; tool action `release_lock`; operator-only). It is diagnostic and force-clean only when uncontested. It refuses (CLI exit 2, `ok:false` with a `reason`) unless (a) the recorded runner pid is dead, (b) the run is not held at a gate or parked on a machine wait (those keep a legitimate runner contract — answer with `release` or `stop` instead), and (c) two consecutive child-probes 100 ms apart both acquire. On success it unlinks nothing — a free lock needs no cleanup and deleting a lock file while racing is exactly the hazard — it reports `lock:free` and `wait` may resume the run. On a contested probe it prints who is believed to hold the lock (`/proc/*/fd` holders with pid and argv, `/proc/locks` lines for the inode) and refuses. **Limitation, stated honestly:** when the kernel still reports the lock held but every visible-holder scan is empty and the runner pid is dead — the cross-namespace stranded case — the hatch cannot release it; it returns `stranded:true` with the forensic dump and says so: the only recovery is a fresh run under a new lane key. A fake success would send the operator back into a wedged wait.

## Runs root, identity, and the trust boundary

Runs live under `<runs_root>` = `$WF_RUNS_ROOT` when set (absolute dir), else `<hermes_home>/workflows`, where `<hermes_home>` is the *resolved* profile home (core's `get_hermes_home()` when importable — so a profile-scoped door on a supervisor/multiplexed host uses the profile's home, not the launch-root `$HERMES_HOME` — else the raw `$HERMES_HOME`) — one resolver shared by door, runner, dashboard, and liveness. Pointing `WF_RUNS_ROOT` at a shared directory lets runs created by a named profile survive deletion of that profile: `wait`, `status`, and the dashboard read them from anywhere. A run's `run.json` gains identity keys ONLY when derivable (a solo default-profile run with no `WF_RUNS_ROOT` adds nothing): `dispatched_by` (launcher profile name), `launch_root`, `team`, `lane_key`, `targets[]` (distinct node profiles), `graph_source` (when replaying a provenance-carrying library graph). Every child spawn carries the absolute run dir so its `inbox` pull resolves without guessing the root. TRUST BOUNDARY: a shared `WF_RUNS_ROOT` is COMMON TRUST — same UID, any profile that can reach the runs root may read, steer, and stop every run there. `dispatched_by`/`owner`/`source` stamps are provenance, not access control; nothing enforces them. Do not treat team fields as an ACL, and do not share a runs root across trust domains — the plugin has no isolation to offer there.

## Library provenance

`save` accepts an optional `source` (≤200 chars). When supplied — or when the saving door runs under a named profile — the library entry records `{owner, source, saved_at, source_digest}`; a default-profile save without `source` writes exactly the pre-1.1 bytes, and legacy entries list as always. `library` shows the fields only when present; `run from:<name>` copies the stamp into run.json as `graph_source`. Provenance is attribution, never permission: no veto, no ACL, no migration of old entries.
